수집 → 재학습 → 배포 → 감시를 스케줄러와 GitHub Actions로 엮었습니다. 동기화가 5일간 조용히 죽어 있던 사고를 겪은 뒤 모든 단계에 실패 알림을 붙였습니다

예측 검증

신뢰도가 −61로 뜨던 원인을 추적하니 단종 품목 한 건이 평균을 148%p 끌어올리고 있었습니다. 산식은 그대로 둔 채 정상화했습니다

자재 소요

부자재 소요를 판매 예측이 아닌 생산 필요량으로 계산하도록 바꿔 거짓 경보 13건을 걷어냈습니다

출고 최적화

요일 판매 지수로 회차별 커버를 환산했습니다. 출고를 절반으로 줄여도 결품률은 그대로였습니다

예측 지평

롤링 백테스트 5회로 3·4·5·6개월을 비교했습니다. 진짜 위험은 정확도가 아니라 편향이었습니다

고객 행동

회차 전환 퍼널에서 2회차가 갈림길임을 찾았고 매장별 재구매율 11%p 격차를 수치로 잡았습니다

경쟁 분석

가격은 중위권인데 카테고리 검색 점유율이 0~11%였습니다. 노출이 비어 있었습니다

업무에 미친 효과

단가·인건비 정보를 갖고 있지 않아 금액 환산은 하지 않았습니다. 수량과 판단 건수로만 적었습니다.

물류 부하

매장 39곳 × 주 3회 = 주 117건의 출고 판단을 자동 산출합니다. 현장이 쓰던 엑셀 양식 그대로 나오므로 옮겨 적을 일이 없습니다

대응 시점 확보

예측 지평을 4개월로 늘려 향료 조달 90일을 덮습니다. 발주 데드라인이 지난 자재를 즉시 식별합니다

환산 기준 · 단가·물류비·인건비는 보유하지 않은 정보라 비용 절감액을 추정하지 않았습니다. 수량·건수는 시스템이 실제로 산출한 값이며, 출고량 감소는 안전일수 0~10일을 놓고 출고일 4회·조합 3,804건을 시뮬레이션해 결품률과의 교환비를 확인한 뒤 정한 결과입니다.

운영 환경과 이 페이지의 관계
여기 실린 시스템은 실제 회사 운영 환경에서 매일 돌고 있는 파이프라인입니다. Supabase(PostgreSQL)에 원천을 적재하고, 로컬 스케줄러와 GitHub Actions가 수집·재학습·배포·알림을 무인으로 수행하며, 구매팀은 Notion에서 발주를 기록하고 대시보드는 사내에 배포되어 실무에 쓰입니다.

이 페이지는 그 시스템의 산출물을 가명 처리해 공개용으로 재구성한 사본입니다. 브랜드·제품·자재·매장·거래처명은 모두 가명이고 매출과 고객 수는 지수화했습니다. 재구매율·전환율·예측 오차 같은 비율 지표는 분석 논리를 보이기 위해 원본 값을 그대로 두었습니다.
